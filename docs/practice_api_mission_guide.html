Practice API 미션 진행 가이드

이번 문서는 과제를 어떤 순서로 진행하면 되는지, 브랜치는 어떻게 나누고, FastAPI 파일은 어디에 만들고, Swagger와 PR은 어떻게 확인하면 되는지 그림처럼 정리한 가이드입니다.

브랜치 전략 dev에서 기능 브랜치를 따고, PR로 dev에 병합한 뒤 최종 반영을 main에 합니다.
작성 파일 app/apis/practice_apis.py에 router와 API 5개를 작성합니다.
연결 파일 app/main.py에 practice router를 등록해야 Swagger에 보입니다.
완료 증거 Swagger 테스트 성공, PR 리뷰, dev 및 main 병합 내역이 필요합니다.

1. 이번 과제의 목표

이번 과제는 브랜치 전략을 실제로 적용하면서 FastAPI API 5개를 작성하는 것입니다. API 자체는 진짜 DB를 쓰지 않고, 과제에서 제공한 user_list라는 Python 리스트를 임시 저장소처럼 사용합니다.

쉽게 말하면

practice_apis.py라는 새 API 파일을 만들고, 그 안에 회원 조회/추가/수정/삭제 API를 만든 뒤, main.py에 연결해서 Swagger에서 테스트하면 됩니다.

2. 우리 팀 브랜치 전략

팀에서 말한 방식은 순수한 GitHub Flow라기보다는 dev 브랜치를 둔 GitHub Flow 변형입니다. 초보 팀이 과제 미션을 모아서 확인한 뒤 main에 반영하기 좋은 방식입니다.

기준 브랜치 main

최종 제출용 브랜치입니다. 검증된 결과만 들어가야 합니다.

개발 통합 dev

팀원 feature 브랜치의 작업물이 먼저 모이는 브랜치입니다.

개인 작업 feature/...

각 팀원이 실제 코드를 작성하는 브랜치입니다.

브랜치 흐름
1 main 준비 최종 제출용 기준 브랜치입니다.
2 dev 생성 main에서 만들어 개발 통합 브랜치로 사용합니다.
3 feature 생성 팀원은 dev에서 각자 기능 브랜치를 만듭니다.
4 PR과 병합 feature -> dev, 최종 확인 후 dev -> main으로 병합합니다. 
main
  ↑ 최종 PR merge
dev
  ↑ 팀원별 PR merge
feature/practice-api-router
feature/practice-api-validation
feature/practice-api-test
헷갈리지 말 것

작업 코드는 main에서 바로 작성하지 않습니다. 각자 feature 브랜치에서 작업하고, PR 리뷰를 거쳐 dev에 합칩니다. 마지막에 dev 전체가 잘 동작하면 main으로 올립니다.

팀장이 먼저 할 일: dev 브랜치 만들기

팀장이 먼저 main에서 dev 브랜치를 만들고 원격 GitHub에 올려야 합니다. 그래야 팀원들이 같은 기준점인 dev에서 각자의 feature 브랜치를 만들 수 있습니다. 

git switch main
git pull origin main
git switch -c dev
git push origin dev

팀원이 그다음 할 일: dev에서 feature 브랜치 만들기

팀원은 main에서 바로 브랜치를 따기보다, 팀장이 올려둔 원격 dev를 기준으로 자신의 작업 브랜치를 만드는 것이 좋습니다. 

git fetch origin
git switch -c feature/practice-api-something origin/dev
정리

팀장: main -> dev 생성 후 push
팀원: dev -> feature/... 생성 후 작업
PR: feature -> dev
최종 PR: dev -> main

3. 전체 진행 순서 로드맵

준비
1 팀장이 dev 생성 main에서 dev를 만들고 GitHub에 push합니다.
2 팀원이 dev 받기 origin/dev를 기준으로 각자 작업을 시작합니다.
3 feature 브랜치 생성 작업자는 dev에서 feature/practice-api를 만듭니다.
4 작업 파일 확인 app/apis/practice_apis.py와 app/main.py를 준비합니다.
아래 단계에서 실제 FastAPI 코드를 작성합니다
코드 작성
5 router 만들기 APIRouter로 practice API 묶음을 만듭니다.
6 user_list 넣기 과제에서 준 회원 3명의 데이터를 그대로 넣습니다.
7 요청 모델 만들기 회원 추가/수정용 Pydantic 모델을 만듭니다.
8 검증 함수 만들기 이메일 정규표현식, 비밀번호 조건, 나이, 이름 길이를 검사합니다.
그다음 API 5개를 하나씩 만듭니다
API 구현
9 조회 API 전체 조회와 id별 상세 조회를 만듭니다. 없는 id는 404입니다.
10 추가 API 입력값을 검증하고 새 id를 자동으로 만들어 user_list에 추가합니다.
11 수정 API 입력된 항목만 수정합니다. 아무 항목도 없으면 400입니다.
12 삭제 API id로 회원을 찾아 user_list에서 삭제합니다. 없는 id는 404입니다.
마지막으로 서버에 연결하고 GitHub에 증거를 남깁니다
검증/병합
13 router 등록 app/main.py에서 practice router를 FastAPI app에 추가합니다.
14 Swagger 테스트 http://localhost:8000/docs에서 API 5개를 확인하고 테스트합니다.
15 PR 리뷰 feature -> dev PR을 만들고 팀원 리뷰를 받습니다.
16 최종 병합 dev -> main PR을 만들고 과제 제출용 최종 상태를 만듭니다.

4. 파일 안에 들어갈 것

이번 미션의 핵심 파일은 app/apis/practice_apis.py입니다. 이 파일 안에는 아래 요소들이 순서대로 들어가면 이해하기 쉽습니다.

API 5개를 파일 5개로 나누지 않습니다

과제 조건이 app/apis/practice_apis.py에 router를 작성하라고 되어 있으므로, 최종 결과물에서는 API 5개가 하나의 practice_apis.py 안에 있는 것이 가장 안전합니다. 브랜치는 나눠도 되지만, 파일은 최종적으로 하나에 모읍니다.

순서 요소 역할
1 import APIRouter, HTTPException, Pydantic 모델, 정규표현식 모듈 등을 가져옵니다.
2 router APIRouter(prefix="/practice_api", tags=["Practice API"])처럼 API 묶음을 만듭니다.
3 user_list 과제에서 준 회원 데이터를 그대로 넣습니다. 이번 미션에서는 임시 DB 역할입니다.
4 Request 모델 회원 추가용 모델과 회원 수정용 모델을 만듭니다.
5 Helper 함수 비밀번호 제거, id로 회원 찾기, 이메일/비밀번호 검증 같은 반복 작업을 함수로 분리합니다.
6 API 5개 전체 조회, 상세 조회, 추가, 수정, 삭제 API를 작성합니다. 
# app/apis/practice_apis.py 의 대략적인 모양

from fastapi import APIRouter, HTTPException

router = APIRouter(prefix="/practice_api", tags=["Practice API"])

user_list = [...]

# 2. 검증 함수
# 3. password 제거 함수
# 4. id로 user 찾는 함수

@router.get("/users")

    ...

    ...

팀원이 API를 나눠서 만들고 싶다면

API 5개를 역할별로 나눠 맡는 것은 가능합니다. 다만 파일을 5개로 쪼개기보다는, 하나의 practice_apis.py를 순서대로 완성해 가는 방식이 좋습니다. 같은 파일을 동시에 많이 고치면 충돌이 날 수 있으므로, 가능하면 아래처럼 순차적으로 PR을 올립니다.

추천 분담 흐름
1 기본 틀 PR practice_apis.py, router, user_list, GET 2개를 작성해 dev에 병합합니다.
2 생성/수정 PR 최신 dev에서 새 feature를 만들고 POST, PATCH, 검증 로직을 추가합니다.
3 삭제/등록 PR DELETE API와 main.py router 등록을 추가합니다.
4 테스트/최종 PR Swagger에서 5개 API를 확인한 뒤 dev -> main으로 최종 병합합니다.

5. API 5개를 그림처럼 보기

GET 전체 조회 /practice_api/users

모든 회원을 보여주되 password는 빼고 반환합니다.

GET 상세 조회 /practice_api/users/{user_id}

id로 한 명을 찾습니다. 없으면 404입니다.

POST 회원 추가 /practice_api/users

입력값을 검증한 뒤 새 id를 만들어 추가합니다.

PATCH 회원 수정 /practice_api/users/{user_id}

age, email, password 중 들어온 값만 수정합니다.

DELETE 회원 삭제 /practice_api/users/{user_id}

id로 회원을 찾아 리스트에서 제거합니다. 없으면 404입니다.

6. 구현할 때 꼭 확인할 규칙

비밀번호는 조회 응답에서 제외

GET API나 생성/수정 후 응답에서 password를 그대로 보여주면 안 됩니다.

없는 id는 404

상세 조회, 수정, 삭제에서 id가 없으면 HTTPException(status_code=404)를 사용합니다.

빈 PATCH body는 400

수정 API에서 아무 필드도 안 보내면 400 Bad Request를 반환합니다.

email은 정규표현식으로 검증

과제 요구사항에 정규표현식 활용이 명시되어 있으니 직접 regex를 써야 합니다.

email은 생성 시 중복 불가

POST에서 이미 있는 이메일이면 실패해야 합니다.

password 조건

대문자, 소문자, 특수문자를 각각 1개 이상 포함하고 8~20자여야 합니다.

7. Swagger 테스트 순서

서버를 실행한 뒤 http://localhost:8000/docs에서 아래 순서대로 테스트하면 됩니다.

  1. GET /practice_api/users로 기본 회원 3명이 보이는지 확인합니다.
  2. GET /practice_api/users/1로 홍길동 정보가 보이는지 확인합니다.
  3. GET /practice_api/users/999가 404를 반환하는지 확인합니다.
  4. POST /practice_api/users에 정상 데이터를 넣어 회원이 추가되는지 확인합니다.
  5. 잘못된 email, 짧은 이름, 14세 미만 나이, 약한 비밀번호가 실패하는지 확인합니다.
  6. PATCH /practice_api/users/{id}에서 일부 필드만 수정되는지 확인합니다.
  7. PATCH에 빈 body를 보내면 400이 나오는지 확인합니다.
  8. DELETE /practice_api/users/{id}로 삭제 후 전체 조회에서 사라졌는지 확인합니다.

정상 POST 예시

{
  "name": "김철수",
  "age": 20,
  "email": "chulsoo@example.com",
  "password": "Password123!"
}

실패해야 하는 POST 예시

{
  "name": "김",
  "age": 12,
  "email": "wrong-email",
  "password": "1234"
}

8. GitHub에 남겨야 하는 증거

과제 완료 조건에는 코드만 있는 것이 아니라 브랜치 전략에 따라 병합한 과정도 포함됩니다. 그래서 GitHub에 아래 기록이 남아야 합니다.

GitHub 증거
1 브랜치 분기 dev와 feature/... 브랜치가 있어야 합니다.
2 Commit 작업 내용이 commit으로 저장되어야 합니다.
3 PR Review 팀원이 PR을 보고 승인하거나 코멘트를 남겨야 합니다.
4 Merge feature -> dev, 이후 dev -> main 병합 내역이 보여야 합니다.
